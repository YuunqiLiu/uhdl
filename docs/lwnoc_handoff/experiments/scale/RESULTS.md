# 规模实验：设计装不进上下文时，LLM 还能不能分析

## 设计
8×8 mesh NoC，64 个 5 端口路由器（D1 的 noc_sw，W=38、D=4、TW=6），XY 路由，外加一条看似合理的路由例外：router (5,2) 把发往第 7 列的流量送往西边。
这条例外会造成 48 对源和目的节点之间永远送不到（报文在 router 20 和 21 之间来回弹，即活锁）。

## 三种表示（功能等价，用 2 万周期随机流量逐周期比对，22.6 万个 flit，0 差异）
| 表示 | 内容 | token（o200k） |
|---|---|---|
| R1 扁平 RTL | UHDL 生成的 66 个 .v 文件（每个路由器路由表不同，所以是 64 个不同模块） | 1,105,325 |
| R2 UHDL 源码 | mesh_gen.py（新语法） | 2,532 |
| R3 参数化 SV | noc_sw.sv + mesh_noc.sv（generate 循环 + 常量函数算路由表） | 3,709 |

## 题目（QUESTIONS.md）与标准答案（answer_key.json）
路径两题、零负载延迟、FIFO 总存储位数、不可达的节点对、某路由器的流量来源、活锁行为，共 7 题。
标准答案由扁平 RTL 的 4096 对节点逐一仿真得到（`_eval/tb_gt.sv`、`gt.txt`）。

## 结果（Opus，每种表示 2 个样本，可用任意工具）
| | 正确 | 总 token | 时长 |
|---|---|---|---|
| R1a 扁平 RTL | 7/7 | 84.3k | 441s |
| R1b 扁平 RTL | 7/7 | 96.0k | 334s |
| R2a UHDL | 7/7 | 47.9k | 336s |
| R2b UHDL | 7/7 | 45.3k | 208s |
| R3a 参数化 SV | 7/7 | 48.1k | 369s |
| R3b 参数化 SV | 7/7 | 47.9k | 412s |

- 6/6 全对。所有 agent 都用 4096 对节点的全量仿真验证了答案。
- R1 的 agent 从来没有把 110 万 token 读进上下文。它们只读了一个路由器文件，发现"64 个路由器只差路由表"，然后写脚本解析全部路由表和顶层连线，再用仿真确认。
- 代价是 R1 的 token 大约是另外两种的 1.9 倍（平均 90k 对 47k）。
- R2 和 R3 几乎一样：对规整的结构，手写参数化 SV 和 UHDL 源码同样紧凑。

## 结论
1. 对会用工具的 agent，"装不进上下文"不等于"没法分析"：它们会把设计当数据处理（grep、解析、仿真），而不是当文章读。
2. 但能这样做，前提是设计规整：扁平网表里能看出重复结构，脚本才能把它压缩。不规整的手写逻辑（例如 lwnoc STS 的 32.6 万 token 叶子 SV）没有这种捷径。
3. 紧凑的源码表示（无论 UHDL 还是参数化 SV）把分析开销减半，并且让"意图"可读：R2 和 R3 的 agent 直接看到了 `ROUTE_OVERRIDES`，R1 只能从 64 张表的差异里反推。
4. 这次没有测"修改"：在 R2 和 R3 里改路由只需改一行，在 R1 里要改 64 个文件，或者先重建生成器。

# 修改任务（mod/MOD.md）
同一个 mesh，提四项改动：
1. 去掉路由例外；
2. 改成先 Y 后 X 路由；
3. 中心 4×4 路由器的 FIFO 深度改为 8；
4. 新增 `l_out_src` 端口，flit 要带上源节点 ID。

评分方法：和我的参考实现（`mod/_eval/mod_ref`）在 3 万周期随机流量下逐端口、逐周期比对，分轻载、重载、慢接收三段。
评分脚本自测：参考实现对自己 0 差异；故意漏掉改动 3 的版本报出 61464 处差异。

| | 结果 | 总 token | 时长 | 改动量 |
|---|---|---|---|---|
| R1a 扁平 RTL | PASS | 120.6k | 1037s | 从 RTL 反推，重写了一个 231 行的生成器，输出参数化的 router.v 和 mesh_noc.v |
| R1b 扁平 RTL | PASS | 94.7k | 520s | 写了一个 77 行的脚本，直接改 64 个路由器文件的文本 |
| R2a UHDL | PASS | 45.0k | 214s | +16 / -13 行 |
| R2b UHDL | PASS | 45.9k | 185s | +18 / -13 行 |
| R3a 参数化 SV | PASS | 41.4k | 110s | +14 / -13 行 |
| R3b 参数化 SV | PASS | 63.7k | 562s | +11 / -10 行 |

- 6/6 全部和参考逐周期一致。
- 改扁平 RTL 的开销是另外两种的 2.2 倍左右（平均 108k 对 46k 和 53k），耗时也长 2 到 5 倍。
- 两个 R1 agent 都没有手改代码。一个是"反编译"：从 RTL 里重建出一个生成器；另一个用脚本批量改文本。
- UHDL 和参数化 SV 打平：改动都在十几行左右，token 也相近。

## 结论（分析 + 修改）
- 紧凑源码（UHDL 或参数化 SV）在分析上省约 1.9 倍，在修改上省约 2.2 倍。扁平 RTL 仍然能用，但要先"反推出源码"，这部分开销每次都要付。
- 对规整的 mesh，UHDL 和参数化 SV 没有差别。
